# AGENTS.md

## Project overview

This is a HubForge project managed by the `@gainsight-hub/hubforge` CLI (`hf`). The primary artifact is **widgets** — each renders in its own container on a community page. Sitewide **scripts** and **stylesheets** are an optional layer for analytics, shared utilities, custom fonts, or global theming. Per-widget **connectors** define the outbound HTTP calls each widget makes.

- `extensions_registry.json` and `connectors_registry.json` are **committed source of truth** — do not hand-edit them casually. Widget and connector entries are regenerated by `hf build` from `widgets/<name>/` sources. Script and stylesheet entries live in the registry and are managed by the `hf script` / `hf style` subcommands (which also create the corresponding `.js` / `.css` files under `scripts/<name>/` and `stylesheets/<name>/` for local entries).
- Widget sources live under `widgets/<name>/`. Optional sitewide sources live under `scripts/<name>/` (a single `script.js`) and `stylesheets/<name>/` (a single `style.css`). External URL entries do not have any corresponding file.
- Add or remove sitewide assets via the CLI (`hf script new/link/rm`, `hf style new/link/rm`) rather than editing files manually — the CLI updates the registry entry and, for local scripts, creates or deletes the corresponding folder.

## Common commands

Widgets first (this is the main workflow):
```sh
hf create                      # scaffold a new widget under widgets/<name>/
hf preview                     # dev server + CC pairing (existing)
hf list                        # list all discovered widgets
hf connector test <name>       # smoke-test a widget's connector
```

Sitewide assets (optional):
```sh
hf script new <name>           # create scripts/<name>/script.js and add a registry entry
hf script link <url>           # add an external CDN registry entry (no file)
hf script rm <name>            # remove local folder AND/OR registry entry
hf style  new <name>           # create stylesheets/<name>/style.css and add a registry entry
hf style  link <url>           # add an external CDN registry entry (no file)
hf style  rm <name>            # remove local folder AND/OR registry entry

# Flags on new / link:
#   --placement head|bodyStart|bodyEnd     (scripts only)
#   --attr key=value                       (repeatable)
#   --page-type <type>                     (repeatable; default: global)
#   --description <text>
```

Build & CI:
```sh
hf build                       # rebuild every widget + regenerate the registries
hf build --no-widgets          # skip the per-widget build; registries only
hf build --validate            # non-zero exit on drift (CI gate)
```

**Before committing widget source changes, run `hf build`** at the project root. It rebuilds every widget's `dist/` (the platform serves widgets from those built directories, so `widgets/*/dist/` MUST be committed) and refreshes the registries. CI's `hf build --validate` fails on drift.

## Repository layout

```
hubforge.json                   # project metadata (CLI + template version)
extensions_registry.json        # committed; widgets/connectors regenerated by hf build; scripts/styles managed via hf script/style
connectors_registry.json        # committed; regenerated by hf build from per-widget connectors.json
.github/workflows/hubforge.yml  # CI: hf build --validate (via reusable action)

# Primary: widgets
widgets/<name>/
  widget.json                   # widget config (schema: online docs)
  connectors.json               # optional — connectors and/or composite_connectors
  dist/content.html             # entry file (convention: source.path = "dist")

# Optional: sitewide scripts and stylesheets
# (Each entry is in extensions_registry.json. Local entries also have a file here.)
scripts/<name>/
  script.js                     # source for a local script entry
stylesheets/<name>/
  style.css                     # source for a local stylesheet entry
```

## What `hf build` validates locally

The CLI produces a well-formed registry and defers platform validation to the service. Locally enforced (details in the portal above):

- JSON validity of `widget.json` and `connectors.json`.
- `widget.json` declares exactly one of `source` or `content`.
- For `source` widgets, the entry file resolved from `source.path` + `source.entry` exists on disk.
- `source.path` and `imageSrc` reject `..` and leading `/`.
- Connector permalinks are unique across single + composite connectors.
- Script / stylesheet entries pointing at local paths have the file on disk (warning by default, error under `--strict`).

Everything else — property schemas, SDK APIs, CSP rules, publishing pipeline — is documented online.
